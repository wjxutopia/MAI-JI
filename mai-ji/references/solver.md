# 需求规范化与当前买法求解

## 锁住需求和履约

将需求拆成真实食品叶子项：identity（当前核实的准确商品/口味/规格身份，不是模糊名称）、name、spec、quantity、complete。普通标准单不设独立特制字段，也不要求配料回显；只有用户明确要求或已知原单备注时，才用可选 notes 保存适用于该食品的短文字要求。全单备注使用履约 remark_digest；不得把未知的明确备注当空值。

对子套餐逐级展开：每份子项数量乘父套餐份数，合并商品身份、规格和明确备注完全相同的叶子项。费用、餐具费不是食品叶子。不能用名称近似把薯条变成中薯条、可乐变成无糖可乐、冰饮变成热饮。跨编码映射只有当前详情确证同商品同规格时才建立，不建立永久猜测字典。

`complete=true` 断言商品身份、口味、规格、数量已确认，且已知明确备注已保留。普通单无配料字段不使其不完整；不声称读到了隐藏的历史配料。spec 为空字符串只允许商品确实无独立规格。保存的身份每次重新用当前详情验证，不能将旧 code 永远视为同货。底层必选参数依当前菜单可靠默认值内部构造；冲突时不能猜选。

规范化履约包含全部键：

```json
{
  "storeCode": "当前真实店码",
  "orderType": 1,
  "beType": 1,
  "beCode": "",
  "address_binding": "",
  "takeWayCode": "本次核价真实编码",
  "reservationDate": "",
  "needTableware": false,
  "remark_digest": "以digest计算的备注指纹"
}
```

立即外送：orderType=2、beType=2、beCode=真实配送业务码、takeWayCode空字符串；address_binding为当前地址ID与完整地址/收件信息组合的本地 SHA256 指纹，只有哈希参与授权，不落原文。标点或顺序需确定性规范化，不能把不同地址归为相同。此指纹不是匿名化承诺，不公开、不打包；地址原文仅在当前MCP会话内比对。预约/得来速/团餐不在本版执行范围，不能改成普通立即外送绕过。

## 先重核原单，再找候选

1. 读取原单完整应付，金额转换整数分；同时核查当前状态和支付截止。
2. 用当前真实完整商品、明确备注和履约重核原单。原优惠不可恢复、关键费用缺失或重核不一致时，不计算精确“可省 X 元”，输出无法完成严格复核及已知原因。普通标准单不因没有配料字段额外补问。
3. 无原单时，按本次明确口述需求或获准复用的模板构造可售单点或当前套餐结构，获取完整基线；直接口述不要求先保存模板或先建原单，缺决定性条件才最小澄清。旧模板里不保存价格。
4. 获取当前店/渠道菜单，找出目标单品和可能包含目标的套餐/组合，再取相关详情。不能只凭标题筛出最低价就结束。
5. 针对实际 rounds，枚举满足目标的选法、父项数量及剩余单点，遵守 min/max 与必选。底层默认选项按当前菜单可靠信息构造，不把接口参数变成用户配料问卷。可按实际商品池去重，但不同报价来源或优惠条件不应误合并。
6. 先检查严格硬约束；使用 guard compare 分类，只有 equivalent 才能标等价。目标被完整保留但额外商品同价/低价才作为可选增益；少目标、换规格、丢备注或履约变更不是增益。
7. 将有意义候选逐一官方整单核价，计入配送、打包、餐具和券。营销价、diffPrice 求和只作预筛，不作最终报价。查不到可单点 SKU 的套餐子项不能独立核价硬凑。
8. 保留当前基线、一个最优已核验等价候选、至多一个有意义增益。若照旧与最优完全相同则合并；没有候选更省时诚实保留。

## 有界搜索，不假称全局最优

正常单优先检查相关组合，不全店暴力请求。第一轮最多核价12个完整候选；若已能证明一个实际更省结果且剩余候选无明确改善依据，可以停止。预算/多人可在当前会话把候选数扩大至24；再多则解释“本次已核验范围”，或按用户追问继续。这个上限是性能策略，不是官方限流契约。不得把未核价候选称最低。

每次比较结论和决策卡都明确写“本次已核验范围内”，可用短句“本次已核验范围内：……”。即便发现更低价，也只报告已核验候选之间的差额，不将有限搜索称为全局最低。

库存和时段以当前真实返回为准，不靠本地早午餐固定时间猜。菜单响应截断先重取更窄范围；不能把被截断的候选当不存在。

## 优惠券

仅使用当前门店/渠道返回、可合法传入的券编码。可用性以完整官方核价为准，不自行发明 stackable、threshold 字段。无效券导致核价失败，排除此分支，不回落零元。含券原单重建不出有效ID时降级，不能拿无券价与带券原单算“省钱”。本版不自动领券、不买会员；券依赖的替换因占用与释放未实测，保留建议，不执行。

## 额外商品与明确备注例外

多一杯不想喝的饮料不是默认福利。卡片必须写商品名、规格、数量和额外情况，即使历史接受过、同价或更便宜也不能静默纳入。

用户明确说“不要酱”等要求或原单已知存在明确备注时，保留对应食品范围和原意，纳入需求和授权指纹。只有当前工具能可靠传递且后续能核对该要求时才给创建/替换编号；无法做到时保留原单并说明该项限制，最短下一步可为回原生界面处理这条备注。仅靠金额一致、默认选项或请求提交成功不能证明明确备注已保留。没有备注例外的标准单不走此分支。

旧模板存在非空 modifications 时只进入 review_required，不把编码猜成标准出品。按 memory.md 仅核对该旧要求，确认文字备注后可显式更新模板；不要求重新描述整单。

## 多人预算模式

把人数视为信息，不视为每人一堡一饮的自动规则。必须有用户说明或明确默认并确认的餐量目标/必需类别。比如“8人、300元”仍缺食量和必需品；最小追问一次“每人至少一个主食吗，有没有忌口？”而不是逐人采访。用户明确“8份主食、至少4份薯条、不要饮料”则这些是硬约束。

按整数需求向量生成可覆盖的单品/套餐组合，用当前完整报价选择预算内候选。不能通过漏餐、降低规格、改店改地址、加不接受的饮料来声称达标。没有预算内可行解则展示最低已核验可行价和超额，不自动下单。轻量模式不保证全局数学最优，不做群组记忆、AA分账或营养建议。
