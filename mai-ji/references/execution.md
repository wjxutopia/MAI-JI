# 编号即执行：授权与异常状态机

## 正常交互

一次触发 → 内部读取/求解/核价 → 一条编号决策消息 → 用户一次编号 → 执行并核验 → 用户自行支付。正常路径不再加“确认下单吗”。允许在流程有关键歧义时最小澄清，不为了顺畅隐藏缺失事实。

## 发卡前

1. 确认作用账户scope、稳定session、唯一需求来源和履约。启动时先status；如果同scope存在未解决执行，先只读恢复，不再发创建/替换卡。
2. 存在原单时，核对原单编码、完整费用、明确待支付状态和时间。没有原单的复购/明确需求创建，则从完整需求和当前履约构造并核验基线，不要求先建原单。严格复核无法完成时明确缺项，不把建议做成可执行替换。当前无券到店/立即外送为有限执行范围。普通订单按标准出品，不因缺配料字段补问；已知明确备注无法可靠保留、或券占用不明时不能执行替换。
3. 候选全部在当前条件下完整核价；商品、规格、数量、已知明确备注和授权动作能准确表达，执行参数保留当前会话，不落完整请求或私人地址。
4. 用digest计算完整摘要指纹，offer保存允许字段。有效期取当前时间后最多300秒，且不晚于已知报价/旧单/库存窗口最早截止。状态存储失败时只能建议，不降级为“凭聊天记录防重”下单。
5. 将返回的完整16位卡号、有效截止、每项动作、金额、履约和额外商品发在同一消息，比较结论明确“本次已核验范围内”。保存当前会话的“已展示卡号＋选项映射”。本地offer成功但消息未实际发出/展示记录缺失，不得接受编号。

## 选项规范

- keep：保留卡绑定的当前待支付单，不新建。不称“照旧创建”而实际上重复建单。
- create：没有可复用匹配待支付单时按明确需求创建一个新待支付单。
- replace：明示“新建本方案，核对成功后取消指定旧单”，不是泛泛“要这个”。
- 可选增益必须列出多的商品、规格、数量；原有明确备注仍须保留。只允许本次明确选择后纳入。
- 没有可靠可执行候选则只给建议或保留结论；不要编号一个实际不可执行的替换动作。
- 只要最少必要选项。照旧和更省已相同则合并；不要人为固定三选一。

## 处理编号

1. 确认本会话当前已展示卡仍有效。归属清楚时接受纯编号；归属不明时只接受当前卡的完整“卡号＋编号”，例如 `卡 aaaaaaaaaaaaaaaa 2`（合成ID）或当前ID加冒号和编号。用selection规范化后再执行以下重验和claim。用户指向旧卡、回复含糊、报价已过期时，不猜。无卡的数字无订单写权限。
2. 重新查询原单详情/列表及当前匹配待支付单，重新获取候选合法选配、有效优惠与完整核价。无需每次重新问同一地址，但必须从当前地址簿验证同址。
3. 按runtime.md同规则重建指纹。任何影响选择的变动都invalidate旧offered卡，重发清晰的新卡；不静默接受“只贵一点”。
4. claim原子领取授权。返回失败不得重试业务请求。如果领取后但未begin时发现变化，abort安全结束该receipt，再新卡选择；只要begin过就不能abort解除未知。

纯编号在消息延迟时可能没有可证明的目标卡归属：若宿主提供回复关系，必须核对；上下文不清时设置selection的require_card_id=true，要求当前完整卡号加编号。若用户明确指向旧卡则拒绝，必要时重核并重发；新会话不能凭旧卡号取得执行权限。没有可靠会话路由或展示记录时停止，不靠补卡号弥补。selection只解析文本，不证明有效期或授权，不宣称能识别所有网络延迟的旧裸数字。

## 创建与替换顺序

```text
claim成功
 ├─ keep → 重查仍待支付 → finish(old_pending=true) → 原单唯一入口
 └─ create/replace
      → begin(create)成功并持久化
      → create-order一次
      → record成功/明确失败/未知
      → 详情+列表确认新单与请求一致且待支付
      → verify(new_order_id, matched=true, pending=true)
      ├─ create → 再查新单 → finish(final_new_pending=true)
      └─ replace
           → 再确认旧单仍待支付且新单仍有效
           → begin(cancel, old_pending=true)
           → cancel-order绑定旧单一次
           → record结果
           → 双查：旧单取消/过期，新单待支付
           → finish(final_new_pending=true, final_old_terminal=cancelled/expired)
```

每个begin成功最多对应一个外部写调用。工具响应后尽快record，禁止因为聊天模型“没记清”而再发一次。begin后异常、超时、断线、结果截断都按未知查询。

新单核对至少包含：真实orderId、父及子项编码与每份/总份数、商品口味规格、门店、业务渠道、地址/取餐、时间、餐具、已知明确备注、全部费用与完整应付、明确待支付及真实有效期。普通标准单不额外要求配料回显。存在明确备注例外时，必须有该项可靠传递和核对证据，不能仅凭金额一致或“创建成功”宣称已保留。核价后与创建间存在竞态；有偏差则不取消旧单、不报完成。

## 结果未知与非原子替换

| 情形 | 操作 | 用户指引 |
|---|---|---|
| 创建明确业务拒绝且确定没创建 | record failed，关闭本授权 | 原单不动；想再试必须新报价和再次选择 |
| 创建超时/未知 | record unknown或保留dispatching，先查列表/详情 | 不重复创建、不取消旧单；查不清就停 |
| 新单存在但商品/费用/履约不符 | verify false | 保留旧单，不自动撤新单“回滚”；说明两单状态待人工确认 |
| 新单成功、旧单取消失败 | 保留记录，双查两单 | 列旧/新单摘要、尾号、金额和当前状态；暂停支付，原生页只核对处理绑定旧单，回来只读查状态 |
| 取消响应未知 | reconcile或observe只读补证 | 明确旧单取消/过期且新单核验仍待支付才完成；不再派发取消 |
| 旧单在cancel派发前自然过期/已手动取消 | observe记录绑定旧单终态 | 新单核验仍待支付则可只读完成，无须补发取消 |
| 新旧两单都明确取消/过期 | observe/recover close=true | 结束为未完成，说明两单均不可支付；重新下单须新卡选择 |
| 旧单在中途已支付 | 停止后续取消及新单支付指引，保持阻塞 | 明示不要支付新单；到原生订单页核对已支付旧单，需处理退款/重复餐时联系官方客服；回来只读核查两单，不承诺退款、不自动解锁 |
| 执行后用户重复编号 | 脚本拒绝重复claim/begin | 回报已有执行结果或先查状态，不重复写 |
| 状态DB损坏/不可写/归属不明 | 停止所有写操作 | 保留只读建议和当前状态，不换DB绕过 |

取消失败的具体指引只针对已经确认存在的两单：展示各自门店/商品摘要、尾号、完整金额与当前状态，不给两个支付链接。提示“先别支付；到原生订单页核对尾号……的旧单，仅取消这笔旧单，别误动尾号……的新单；完成后回来叫我‘查一下状态’。”原生页无取消入口时可等待旧单实际失效后回查；不能承诺固定自动失效时间，也不能把用户说已取消当终态证据。若订单号/归属未知，先只读定位，不让用户凭相似摘要盲目取消。

回来后重新查询绑定两单详情和列表。原会话用observe；新会话按status给出的最小绑定信息用recover，禁止抄用旧session去begin。旧单明确取消/过期，且新单此前完整verify通过、当前仍匹配且待支付时，complete=true及final_new_pending=true可只读完成；两单都取消/过期时close=true结束为未完成。新单未知、未核验或已支付冲突时继续停止；若尝试close结束替换，则少一单取消/过期证据也不能收口。complete成功路径允许新单仍待支付，无须新单终态。不因恢复补发写请求。只读完成后，从本次新单查询的真实返回提供唯一正确新单入口与截止时间；没有入口则给已确认尾号，引导到原生订单页支付该单，未知截止不编造。allow_dispatch=false表示不再派发创建/取消，不妨碍用户自行支付。参照runtime.md的精确字段和门槛。

查单找到多个相似候选不能任选一个归为本次创建。查询范围包括调用前后订单差集、时间、店/渠道、金额和商品；仍不唯一就未知。当前API未保证请求幂等/权威不存在证明，列表暂时无新单不是重试许可。

替换不是原子事务，也不具备跨设备锁。用户在其他设备支付/操作会改变状态；预检查通过不等于之后不会变化。新单和旧单都确认后，只提供一个正确订单支付入口与截止；中间态不提供两个链接让用户猜。不要计算“已省钱”直到实际支付可证，未支付只说当前报价低多少。

## 首用与记忆

第一次执行前简短说明会在本机保存最小卡号/订单状态用于防重复，不含支付或地址原文。此操作记录不是常点模板。只有用户另行明确同意保存长期需求才走memory.md；保存需求不是支付、建单或取消授权。

## 精简示例（均为合成演示）

**有可靠增益**：
“本次已核验范围内：原单汉堡1个＋薯饼1份，¥30.00。1｜¥30.00保留原单，不新建。2｜¥27.00，新建同款汉堡1个＋薯饼1份＋小杯豆浆1杯，核对后取消原单；豆浆为新增。同店同址含配送打包。卡aaaaaaaaaaaaaaaa（合成示例），有效至08:03；回复编号执行，最后自行支付。”

**没发现更省**：
“本次已核验的单点和相关套餐里，原单¥30.00已足够省，未发现保持你这份需求的更低报价。保留原单，不新建。”（仅状态可靠时给真实入口）

**无法完整还原**：
“读到这单总额¥30.00且仍待支付；原优惠当前无法重新核价，暂时不能确认等价方案能省多少。先保留原单；请到原生订单页核对原券，回来后我再按可核验条件复核。”不输出可执行替换编号。

**明确备注无法传递**：
“这单已知备注‘不要酱’，当前接口无法可靠保留它；先保留原单。请在原生界面处理这条备注。”只针对已知明确要求，不把普通单缺配料字段当异常。

只读降级始终包含已知事实、具体缺证、当前可确认结论/限制和一条下一步。原券无法重放时可建议回原生页核对原券与可用套餐；费用缺失时先补齐完整费用。不以“不能做”收尾，也不为了生成结果放宽等价。

**未知**：
“创建请求结果还没确认，我已停止，不会再建或取消旧单。先别支付；接下来只查单确认状态。”
