# 记住需求，不把临时订单变成偏好

## 两类本地数据分开

1. 执行日志：卡号、脱敏方案标签、总价、摘要哈希、绑定订单号、单次授权和状态。仅用于当前执行与防重；不自动推导口味或常用门店。首次使用前简短说明最小本地操作记录，不含地址/支付原文。
2. 长期需求模板：只有显式同意及明确保存意图后建立，供“老样子”跨会话读取。保存需求不意味着授权创建、取消或支付。

使用runtime.md中独立DB，不在技能目录、项目公开产物或通用云记忆中散落副本。项目开发日志绝不是用户常点模板。脚本状态里有历史金额不代表允许复购沿用；模板本身不保存价格。

## 首次保存

触发语包括“记住这份早餐”“以后就按这个”“保存为常点”。先核对具体需求已经由用户选择或明确口述，而不是未选择候选；关键规格/履约或已知明确备注仍未知时仅补该项。普通单按标准出品，不设置独立特制属性，不补问用户没选过的配料。

首次未授权持久化时，用一条简短说明和同意请求。列出本次实际要保存的食品、规格、数量、明确备注/限制及必要场景。示例（仅演示）：

> 可以在本机保存“到店早餐”：A堡标准份1个＋薯饼1份，工作日早餐、这家门店、到店取餐。不保存旧价格、支付信息、电话或完整地址；以后说“老样子”会重查当前价格。要保存吗？

若“保存这个”可能指原餐或含新增饮料的方案，只澄清保存对象；本次没选的增益不加入模板。明确保存含增益的完整需求后，才把它作为下次需求的一部分。

用户明确同意后调用consent，再template-save。首次明确说“同意按上述范围保存”可在同一步完成；不能把含糊“好”当订单写授权，且模板同意与订单编号执行是两套不同目的。

已有持久化同意后，后续仍须每次有“以后都这样/保存常点”的显式更新意图。临时加饮料、换门店或为同事点餐不覆盖模板。历史接受的增益只可影响推荐排序，不改变默认食品；本版不自动建立这类软偏好档案。

## 模板内容

- name：用户可辨识的短名称。
- scene：daypart、mode、storeCode、address_label、takeway_label中的必要标签。地址仅用户自定义“公司/家”等标签，不留addressId或地址原文；不能自动从联系人姓名生成标签。
- items：实际确认的食品叶子需求、规格、人类可核对名称及数量；普通单无独立配料属性。仅明确备注例外使用可选notes短文本，例如某食品“不要酱”；不凭历史编码生成备注。历史编码只是身份线索，下次必须查当前详情验证。
- restrictions：用户明确的短限制，如不含某商品；全单食品要求可放这里，下次转为完整需求和本次remark_digest。不得把备注中手机号、地址等私人内容抄入。食物过敏/硬性忌口与本次表达冲突时先澄清，不用历史记忆悄悄改订单，也不保证厨房能完全避敏。

禁止字段：价格、旧套餐买法、原始工具响应、未支付订单对象、支付ID/链接、凭证、完整地址、电话、联系人、私密备注。文本过滤只是辅助，不能证明自然语言绝不含个人信息；保存前必须核对最小化。

## 旧模板兼容

1. 继续使用原DB和scope；升级不清库、不重新获得同意、不改执行派发标记。
2. 旧items的空modifications可兼容，读取时返回无该字段的标准叶子；不改写原存储，不问用户配料。
3. 非空modifications不能判断是当年接口默认编码还是用户明确选择。template-load将该模板放入review_required，不放入可自动采用的templates；template-list仍可查看，auto_reuse_allowed=false。不静默忽略或清空旧值。加载与保存使用相同的完整结构/文本校验；坏JSON、缺字段或私密/多余字段只隔离该条，data=null且不回显原文，其他模板继续可用，原存储保持不变。
4. 只有选中的旧模板需此核对。结合已知明确需求说明这一项；不能解读编码时只问一个问题“这份旧方案有配料记录，这次按标准出品还是保留某条明确备注？”不要求重述整单，不展开配料问卷。
5. 本次选择标准出品仅作用本次。只有用户明确“以后也这样/更新常点”，且持久化同意有效时，才把核对后的需求以标准叶子及可选文字notes保存；无法解释的编码不能原样写入新模板。不因升级自动覆盖。

## 状态与来源

- 待支付单仅是当前执行记录，不自动成为模板。用户主动说保存时，可以保存其已经确认的需求，但需以user_confirmed_request来源写入，不是复制订单对象。
- 未选择的推荐、创建失败、已取消或结果未知的订单不能成为复购基线。不得把这些状态换个标签绕过。
- 从当前已确认需求保存时，不声称已支付、已消费或实际口味得到验证。
- 保存失败如实告知；当前会话可继续，但不能承诺下次记得。

## 老样子读取

按当前scope调用template-load，只有当前同意仍有效才可自动复用。template-list仅供用户查看和管理，不可绕过撤回限制。templates仅是可复用候选，仍按场景匹配；review_required只作核对资料，不构成自动复用许可。先按场景匹配templates，唯一匹配直接采用，多个匹配只澄清一个区分条件；templates无匹配时再按可读场景匹配review_required，命中才核对该旧要求，两组均无匹配才提示无对应方案。若坏记录data=null，说明该模板暂不可读取，不凭ID猜内容或自动覆盖，接受本次完整需求继续。没有模板不统计“最近三单”替代授权；一次提示可先在原生界面选好并提交待支付单、暂不付款、回来“检查刚才这单”，也可直接说完整需求。地址标签必须从本次地址簿唯一匹配；重名/地址变化只问一次确认，不能静默选最近地址。门店营业、可配送性、商品、明确备注、价格均实时重验。

已有唯一匹配待支付单可保留，不重复创建；不匹配的临时单不取消。临时改动只作用本单，除非另有明确长期更新意图。

## 查看、修改、删除、撤回

“看看记住了什么”展示模板的商品、数量、规格、明确备注/限制和脱敏场景；旧编码不可解释时明确标为待核对。“以后改成……”确认作用模板后显式覆盖；有歧义只澄清目标模板。

“删除这份常点”仅template-delete指定ID；“删除全部常点”才explicit_all=true。撤回保存同意用consent granted=false，停止后续保存和自动复用；保留既有模板供template-list查看或删除，并明确说明。template-load在撤回后拒绝；只有用户重新明确同意才恢复复用，不能因又说“老样子”就自动恢复同意。明确“撤回并全部删除”才加purge=true。删除模板不影响真实订单，不删除执行状态解除防重；全数据清除涉及未解决真实订单时先查清状态再受控处理，当前版本不提供一键强制抹除。

## 跨会话验证的含义

离线测试证明相同DB/scope可保存和重读模板、未经同意不可写入。用户已反馈1.1.0的六项宿主体验测试全部通过，包括新会话模板读取和撤回；未取得逐项原始日志。本版1.2.0对标准出品与旧模板兼容另有离线回归，不能将旧版体验反馈扩展为新版、所有渠道和所有异常均已实测。
