# 麦记 · 常点复购与付款前省钱复核

保留用户明确的商品、规格、数量、履约和备注，按当前套餐、单点与可核验优惠重新核价；不擅自换餐，不自动支付。本技能不启动网页、独立 Agent 或定时任务。需要创建或替换订单时，宿主必须具备当前麦当劳 MCP、Python 3.10+ 和稳定的包外本地状态能力；其他宿主须自行验证兼容性。

## 先读、再运行

- 首次使用读取 [运行与本地状态](references/runtime.md)，确定 Python 3.10+ 和独立数据目录。脚本只计算和记录，不调用网络或业务接口。
- 查询、核价或下单前读取 [MCP 实测契约](references/mcp-contract.md)。先发现当前工具参数，再调用；不把本文示例或历史编码当当前可售数据。
- 生成方案时读取 [需求与买法求解](references/solver.md)。
- 展示编号卡、处理编号或恢复中断时读取 [授权与执行状态](references/execution.md)。
- 建立、读取、修改、删除长期模板时读取 [记忆规则](references/memory.md)。
- 验收与适用范围见 [测试与证据](references/validation.md)。禁止将离线通过说成真实下单全覆盖。

## 1. 路由到最短入口

### 老样子 / 再来一单

1. 用 `template-load` 读取仍获同意复用的需求模板。撤回同意时停止自动复用，重新同意才恢复；不从历史订单猜常点。
2. 先按当前场景匹配 `templates`；无匹配时再检查 `review_required`。唯一可复用匹配直接采用，多个匹配只澄清一个能区分的条件。只有待核对旧模板匹配时，按记忆规则仅核对该旧要求，不能当作无模板或自动复用；两组均无对应方案时一次引导：“先在原生界面选好并提交待支付单，暂不付款，再回来叫我‘检查刚才这单’；也可以直接说完整需求。”
3. 查询当前订单。唯一且严格匹配需求和履约的待支付单作为当前基线；其他临时单不替换、不取消、不覆盖模板。多笔无法唯一匹配时只问一次。
4. 重新获取当前菜单、实际子项、有效优惠和完整报价；不使用模板里的旧价格或旧套餐结构。

### 检查刚才这单 / 这单还能省吗

1. 查普通食品订单列表，按明确待支付文字筛选，并查询详情。唯一匹配直接采用；多笔列时间、门店、商品摘要和尾号供选择；用户指定订单号时按该单处理。
2. 按 orderId 合并列表编码与详情履约、费用、子项。只有详情而缺编码时不能凭名字猜。没有待支付单则提示先在原生界面建单，不创建测试单。
3. 锁定同店、同址、同渠道、同取餐方式、同时间和餐具条件。用原商品重核完整金额；原优惠不可重放、费用不齐或商品规格无法还原时说明具体缺项，降级只读建议。

### 直接说完整需求

接受本次明确口述的食品与履约需求；已有唯一严格匹配待支付单时复用，没有时按当前菜单建立完整基线并展示创建编号。缺决定性条件才最小澄清，不要求先保存模板或先建原单。

### 多人 / 总预算

仅在用户主动提出时进入轻量预算优化。提取人数、总预算、必需商品或类别、数量和限制；缺少决定性约束才最小澄清。用当前菜单构造满足硬约束的组合并整单核价；无预算内方案则说明差额，不减少必需商品冒充达标。不保存群组模板、不做 AA、复杂逐人协商或营养医疗建议。

## 2. 在内部比较

- 商品、口味、规格、数量和履约均为硬约束。先拆套餐实际子项，处理父份数乘子项数量，再比较；不根据套餐名或营销标签猜等价。
- 普通商品按标准出品处理，不设独立“特制”属性，不因接口缺少配料字段而询问生菜、酱料、吉士或阻塞正常流程。底层请求如要求默认选项，按当前菜单的可靠默认信息内部处理；默认信息冲突时只处理该项实际异常。
- 用户明确的特殊要求、已知原单备注或已明确的非标准选择作为备注例外保留，不静默丢弃。无法可靠传递或核对时，保留原单并说明该项限制，不展开配料问卷。标准处理不表示已读取隐藏的历史配料。
- 完全满足需求且完整应付金额更低才标“还能更省”。目标全保留、只多商品且同价或更低，单列“可选增益”；多出的商品必须明示，本次不选择就不加入。改商品/规格/数量/履约为非等价变化，不能包装为省钱。
- 已领取不等于当前券可用；只接受当前官方完整核价。券占用/释放未实测可靠的替换只给建议，不取消旧单腾券，不购买会员或自动领券。
- 每次比较结论和决策卡明确“本次已核验范围内”，不承诺全网最低价。零价空回显不是免费商品。
- 只输出一个主要结论，至多一个有意义的额外增益；同一购物篮与同价方案合并，不硬凑三个编号。

## 3. 发一条可执行决策消息

先用脚本 `offer` 保存经脱敏的候选与时效，再展示其返回的卡号。每条编号都必须明写动作、总额、关键商品/额外商品和原单关系。例如（合成演示，不作真实报价）：

> 本次已核验范围内：原单“汉堡1个＋薯饼1份”¥30.00；同店同址，外送含配送和打包。
> 1｜¥30.00 保留原单，不新建。
> 2｜¥27.00 新建“同款汉堡1个＋薯饼1份＋小杯豆浆1杯”，核对成功后取消原单；比原单低 ¥3.00，豆浆为新增商品。
> 卡 aaaaaaaaaaaaaaaa（合成示例）· 有效至 HH:mm · 回复编号执行，最后自行支付。

没有可靠可执行候选时不展示“创建/替换”编号。原单可确认且无需动作时可直接给保留结论；任何支付入口都只能来自本次工具真实返回，不能拼接。未知状态时不提供去支付指引。

## 4. 编号即执行，但先过闸门

1. 正常接受本会话最新已展示有效卡的纯编号。归属不明时要求当前完整“卡号＋编号”，用 `selection` 规范化后重验；旧卡、跨会话卡、展示记录缺失时不能执行。脱离卡片的“好/可以/要这个”不触发写操作；解析成功不代表授权已领取。
2. 执行前重查原单、当前已匹配待支付单、库存/详情、券及完整报价。重新生成相同规范化摘要；任何价格、商品、明确备注、实际默认选配、优惠、履约、原单状态或替换关系变化，废弃旧卡重发。
3. 用脚本 `claim` 原子领取一次授权。领取失败、过期、重复、未知结果未解决、本地状态不可写时，不调用创建/取消。脚本只给本地防重，不是远端幂等或自动交易机器人。
4. 创建前 `begin` 记录一次性派发标记并确认成功；仅发起一次 `create-order`。返回后无论成功/失败/超时，先 `record`；超时按 unknown，查单且不盲目重试。无法唯一找回则停。
5. 新单成功后查询详情和列表，核对完整商品、规格、数量、门店、履约、总额和待支付状态；存在明确备注例外时另核对该要求。普通单不要求额外配料回显。核对失败保留原单并停止；不得自动取消任何一单“回滚”。
6. 替换只有在新单核对成功且旧单再次确认为待支付时，才 `begin cancel` 并取消旧单一次。旧单已自然过期或手动取消时，用 `observe` 记录绑定终态，不伪造取消。失败或未知时说明两单摘要/尾号/金额/状态，暂停支付，按执行参考给原生处理与只读回查下一步，不建第三单。旧单取消/过期且新单核验仍待支付才完成；两单均取消/过期可结束为未完成。新会话 `recover` 只补证/收口，不获得业务派发权。
7. 完成后只给唯一正确订单的真实支付入口与实际截止时间。永不自动支付；“支付完成”仍须查询，不能仅凭用户口述或金额字段判断已支付。

## 5. 保存需求，而不是偷偷学习

首次跨会话保存前列出实际要保存的商品、规格、数量、明确备注/限制和必要场景并征得同意；普通单不增设配料问题。“这个”可能指含增益或不含增益方案时只澄清保存对象。只有“记住这个/以后都这样/保存为常点”等明确意图才写入；同意持久化本身不等于同意自动覆盖模板。当前待支付记录不自动成为模板；用户主动保存时先核对明确选择的需求，不能把推荐或未知/取消/失败订单写成常点。撤回同意后停止保存和自动复用，仍支持查看/删除，重新同意才恢复。

不保存凭证、支付链接、完整地址、电话或联系人。地址在模板中只留用户自定义标签，下次从当前地址簿唯一解析并校验；地址、门店或时间变化重新核价。临时修改仅本次有效。支持查看、修改、删除；拒绝保存不影响本次会话，但不得承诺下次记得。

## 必须停下的情况

连接器不可用、工具结构截断、关键编码缺失、明确备注无法可靠保留、当前默认参数冲突、原单优惠不可重放、费用不齐、状态冲突、候选变化、地址不唯一、授权记录缺失、创建/取消结果未知。只读降级用一条短消息交代已知事实、具体缺证、目前能确认的结论/能力限制和一条最短下一步。原单状态可靠则保留原单；无法严格比较时不报精确节省、不发不可执行替换编号。普通单缺配料字段不在停止条件中。
